# Notebook Making

> **For every figure/plot in a notebook, follow the `scientific-figures` skill**
> (figure rule set: density-based system-design plots, minimal legends, colorbar
> geometry, captions, `.drawio`+matplotlib workflows, table styling) on top of the
> `report-figures` canonical theme.

A study notebook is the **"what the run(s) MEAN"** layer (ADR 0007:
`ResearchProject/systems/<name>/hypotheses/<sweep>/`). It is not a scratch log —
it is a self-contained narrative a future reader (or you, after compaction) can
read top-to-bottom and (a) understand *why* the run was made, (b) reconstruct the
simulation setup in their head, and (c) see the results and the takeaway, with
every claim grounded and every artefact traceable to the file that produced it.

Built notebooks are **executed** (`nbconvert`, 0 errors) — the committed `.ipynb`
carries its own outputs. They are generated by a `build_<name>_report.py` script
(`nbformat`), never hand-edited cell-by-cell.

## When a notebook is produced

| Trigger | Notebook | Location |
|---|---|---|
| A **sweep / run-set** finishes (many runs testing one thing) | one per sweep, rebuilt from all runs present | `hypotheses/<sweep>/<sweep>_study.ipynb` |
| A **consequential individual run** — one that has its own `docs/plans/` entry — finishes | one for that single run | `hypotheses/<sweep>/<run>_study.ipynb` (or a dedicated `hypotheses/<name>/`) |
| A trivial / throwaway probe run | **none** | — |

"Of consequence" = there is a **plan** for it in `docs/plans/`. No plan ⇒ no
auto-notebook (keeps noise out). A planned single run gets the *same* narrative
sections below, scoped to one run.

## The auto-build convention (run-machinery, not a CC hook)

The trigger lives in the **run machinery**, so it fires whether the user launches
the run in a terminal or it is launched as a background task — no Claude-Code
session required. Do **not** rely on a `.claude/hooks` PostToolUse hook for this
(it only fires in-session and must guess completion from the command line).

- **Sweeps:** the dispatcher rebuilds the sweep notebook **once, at the end of the
  whole batch** (not per-run — avoids N re-renders of heavy artefacts like GIFs).
  Tail of `scripts/<sweep>/dispatch.py`, after the run loop:

  ```python
  # auto-build: regenerate the sweep study notebook from all completed runs
  import subprocess
  VENV = "/local/data/public/skcb2/tddft/venv/bin/python3"
  STACK = "/local/data/public/skcb2/tddft/inq-stack/python"
  builder = SYS / "hypotheses" / SWEEP_NAME / f"build_{SWEEP_NAME}_report.py"
  subprocess.run([VENV, str(builder)],
                 env={**os.environ, "PYTHONPATH": STACK}, check=False)
  ```

- **Consequential individual run:** the run's own `analyse.py` ends with the same
  tail call to that run's single-run builder. (`analyse.py` is already mandatory
  per the per-run-analyse convention.)

Every new dispatcher / planned-run `analyse.py` **must** end with this tail call —
treat its absence as an incomplete run-machinery change.

## House narrative — cell order (do not reorder)

Build the notebook in this fixed order. Sections 1–4 come **before any result**.

1. **Title + the question.** One H1 line naming the system and the absorber/method,
   then the motivating question in plain language. Set the context: why this run-set
   exists and what decision it informs. A small "where this sits" table vs sibling
   sweeps is encouraged.

2. **Method / analytical formulas — every term defined.** Up front, give only the
   shared **conventions**: unit system, key constants, and a **symbol → meaning
   table** (units + swept ranges). Do **not** dump every formula here. Each
   *formula lives at its point of use* — restated as display LaTeX immediately
   above the cell that computes (or defines) that quantity — see the
   formula-placement rule below. Never show a formula whose terms aren't all
   defined right there. Flag non-obvious numerical requirements (e.g.
   "non-Hermitian ⇒ requires ETRS, not Crank–Nicolson").

### Formula placement — at point of use, one quantity at a time

For any notebook that *derives or computes* analytical quantities (electron-gas
scales, observables, figures-of-merit), do **not** batch a formula dump up front
and the calculations in one big cell later. Instead:

- **Each formula appears immediately above the cell that uses it.** A reader sees
  the equation and the line of code that evaluates it together, never separated.
- **Compute one quantity per (markdown-formula → code) pair, in dependency
  order.** e.g. Fermi wavevector $k_F$ first (formula + its cell), then Fermi
  velocity $v_F$ (formula + its cell), then $E_F$, then $\lambda_F$, … Each cell
  defines just that one variable and prints it with units. Never collapse a
  family of quantities into a single multi-line calculation cell.
- A short **recap table** collecting the family's values at the end of the section
  is allowed (convenience), but it follows the one-by-one derivation, never
  replaces it.
- This refines (not replaces) section 2: the up-front block is conventions +
  symbol table only; the equations themselves are interleaved with the results.

3. **Simulation setup — fully reconstructable.** Give *all* quantities a reader
   needs to rebuild the run in their head, before results: cell/geometry
   (box lengths, slab edges, dx), electronic structure (functional, pseudopotential,
   cutoff), dynamics (propagator, dt, N_STEPS, total time τ), the perturbation
   parameters and their sweep grid, and the initial-state definition (e.g.
   wavepacket k₀, σ, N₀). Pull these from `results/epsilon.txt`-style provenance,
   not from memory.

4. **Source files — linked by path.** A table linking every file that produced the
   run, post-processing, or modelling: the `run.cpp`, the dispatcher, the per-run
   `analyse.py`, the inqview kernels used, this builder, and the per-run provenance
   files. Repo-relative paths.

5. **Results.** Figures + tables, one finding per section with a one-line lead-in
   saying what is plotted (quantity, units, axes). Compare to siblings/baselines
   where relevant. Use the canonical theme; save every figure as `.png`.

### FFT-pipeline panel — every FFT'd signal shown stage-by-stage

Whenever a notebook Fourier-transforms a signal (dipole / current / energy /
density), show the **3×2 pipeline panel**, never a bare spectrum: row 1 **raw |
de-trended**, row 2 **windowed | zero-padded**, row 3 **|FFT| linear | log**. Use
`inqview.visualisation.fourier_panel.fft_pipeline_panel(t, signal, ft, …)` — it
derives every stage from `inqview.analysis.fourier.FourierTransform` itself (same
`_apply_subtract` / window / zero-pad / coherent-gain), so the panel always depicts
exactly what the kernel computes. Annotate the physical band (e.g. plasmon
$\hbar\omega_p$) and the resolution $\Delta\omega = 2\pi/\tau$. The energy axis uses
the **angular** convention $\hbar\omega = 2\pi f\,E_h$ (match `fourier_analysis.ipynb`
`omega_eV` and `pipeline/spectral_weight`).

### Per-run visual intuition — every significant run gets a GIF + energetics

Before any aggregate/comparison plot, **each significant run** carries two
artefacts so the reader builds physical intuition *before* looking at derived
numbers:

- **An xz density GIF** — the time evolution of the density (or the most
  diagnostic category: the wave packet for WP runs, total/Δn for classical) on
  the **xz plane** (the propagation plane), fixed colour scale across frames,
  with the key geometry marked (slab/target plane, absorber edges). This is the
  *first* thing shown for a run — it is the visual sanity check that the run did
  the physical thing it was meant to.
- **The energetics of that run** — energy components vs time
  (total / kinetic / Hartree / xc, and projectile KE for classical), so
  conservation (or, for a non-Hermitian absorber, the intended drain) is visible
  per run.

**What counts as "significant":**

- **An individual consequential run** (its own `docs/plans/` entry), or **every
  run of a small fixed campaign** where each run answers a distinct question
  (e.g. centroid/channeling × cap/nocap) — visualise **all** of them, one
  per-run block each.
- **A sweep** (many runs scanning one parameter) — do **NOT** GIF every run.
  Pick a small set of **representative runs** (e.g. min / mid / max of the swept
  parameter, plus any outlier) and GIF only those; the rest live in the aggregate
  figures/tables. State in the lead-in *which* runs were chosen as representative
  and why, so nothing is silently dropped (no-silent-caps rule).

GIFs are heavy — generate them in the builder (reuse `inqview.pipeline.density`'s
VTI loader / slice conventions), keep them in `figs/`, and embed/reference each in
its run block. Because they are expensive, the auto-build runs **once at batch
end** (never per-run).

### Path-reference figures — do NOT base64-embed heavy media

The builder may **reference figures by relative path** instead of embedding them as
base64 in the cell outputs. **Prefer this for any notebook with GIFs.** Emit a
markdown cell — `![caption](relpath)` where
`relpath = os.path.relpath(fig, os.path.dirname(out_ipynb))` — rather than a code
cell that runs `display(Image(filename=…))`.

- **Why.** Base64-embedding inlines ~1.33× the raw bytes into the `.ipynb`. A
  notebook with dozens of multi-MB GIFs balloons to 30–40 MB, and viewers
  (Jupyter, VS Code, nbviewer) then load slowly or fail to render — the reader sees
  a blank/partial notebook and thinks the content is missing. Path-referenced
  notebooks stay **KB-sized** and the viewer lazy-loads each figure from disk only
  when scrolled into view.
- **The cost** is portability: the figures must travel **beside** the notebook
  (decomposition GIFs in the notebook's folder, PNGs in `<stem>_figs/`, pipeline
  figures under `results/analysis/…`). For this repo that is fine — figures are
  committed next to the `.ipynb`. Verify every reference resolves
  (`os.path.exists`) at build time; a broken relative path renders as a missing
  image.
- **Reference implementation:** `run_notebook_builder.py::img()` (run-notebook
  skill) and `hypotheses/_nbreport.py::embed()` + `set_outdir()` both emit relative
  markdown refs. Small analysis **PNGs** *may* still be embedded if you want a
  truly single-file artefact, but **GIFs and any figure set > a few MB total must
  be path-referenced.**

When a run **failed, crashed, or produced anomalous physics**, add a short
**post-mortem** subsection for it: what was expected, what the run actually did,
and *potential explanations grounded in the actual log/error output* — quote the
relevant log lines/numbers, never a remembered claim. If the logs do **not**
corroborate a previously-asserted failure mode, say so explicitly and correct the
record. (scientific-grounding + verification-user-owns-verdict: present evidence,
don't invent the diagnosis.)

6. **Takeaway.** The bottom line in 2–4 bullets — the headline number(s) and what
   they imply for the decision; keep open questions explicit.

## Grounding & honesty (scientific-grounding rule)

- Cite the method/formula source inline (author–year) near where it is used; add a
  one-line provenance note.
- Label provisional results **PROVISIONAL** with the gate that lifts it (e.g. a
  pending engine regression). Never write "converged"/"shows"/"proves" without
  verification; use "we infer"/"consistent with" for qualified claims.
- Numbers come from run provenance files, never invented.

## Mechanics

- Builder lives beside the notebook: `hypotheses/<sweep>/build_<sweep>_report.py`.
  Pattern: parse each `run_*/results/*.txt` → combined CSV → `nbformat` cells →
  `ExecutePreprocessor` → write executed `.ipynb`. Be **partial-tolerant**: read
  whatever runs exist so an interrupted sweep still builds.
- Run it with the venv interpreter and the stack on the path:
  ```bash
  PYTHONPATH=/local/data/public/skcb2/tddft/inq-stack/python \
  /local/data/public/skcb2/tddft/venv/bin/python3 build_<sweep>_report.py
  ```
- Theme: `from inqview.visualisation import style; style.apply_theme()`. Figures
  `.png` only (file-placement rule). Do **not** preview/Read generated PNGs — only
  the user previews unless asked.
- Worked examples to clone: `hypotheses/cap_Lopt_E10/build_Lopt_report.py`,
  `hypotheses/cap_monomial/build_monomial_report.py`,
  `hypotheses/cap_thin_L5/build_thin_report.py`.

### Reader annotations survive rebuilds (harvest-before-rebuild + sidecar)

Rebuilds regenerate the whole notebook, so the builder must NOT be the home of reader
comments. Two mechanisms (reference impl: `hypotheses/_nbreport.py`):
- **Harvest-before-rebuild.** Every builder cell is stamped `metadata.gen="builder"`
  (+ an `anchor` slug for headed markdown) by `tag_builder()` inside `md()`/`code()`/
  `embed()`. `build()` calls `harvest_user_cells(out_path)` *before* regenerating to
  collect any markdown a reader added (untagged cells), then `reinject()` splices each
  back at its anchor (stamped `gen="user"` so it round-trips every future build);
  orphaned annotations (anchor renamed/removed) go to a "📌 Carried-over reader
  annotations" section, never dropped. Readers may annotate the `.ipynb` directly.
- **Sidecar.** `<stem>.notes.md` beside the `.ipynb` is pinned as a top "📝 Reader
  notes / TODOs" cell each build.
- **Transition:** a pre-tagging notebook (no `gen` tags) harvests as nothing — build
  each notebook **once** to tag its builder cells before readers annotate.

## Definition of done

- Notebook executes to **0 errors**. Heavy media (GIFs) are **path-referenced**,
  not base64-embedded (keep the `.ipynb` small — see "Path-reference figures"); all
  references resolve.
- Sections 1–4 present and *precede* results; every formula symbol defined; every
  source file linked; setup is fully reconstructable.
- For derived/analytical quantities: each formula sits at its point of use and
  quantities are computed **one per cell in dependency order** (no up-front formula
  dump, no batch calculation cell) — see the formula-placement rule.
- Every significant run carries an **xz density GIF + per-run energetics** before
  the aggregate plots; sweeps GIF only **representative** runs (stated, not
  silently dropped); failed/anomalous runs get a **log-grounded post-mortem**.
- The producing dispatcher / `analyse.py` ends with the auto-build tail call.
- Provisional results flagged; sources cited.
- **Reader annotations round-trip a rebuild unchanged** (harvest-before-rebuild):
  builder cells tagged `gen="builder"`; a markdown cell a reader adds survives the
  next build at its anchor.
